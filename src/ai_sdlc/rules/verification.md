> 本规则在任何"声明完成"之前激活 —— 批次完成、阶段完成、流水线完成。
> **没有验证证据就声称完成，不是效率，是不诚实。**

## 反例验收的宿主职责

普通用户表达目标、合法使用方式和范围约束；宿主 Agent 负责内部合同、执行计划和证据，不要求用户填写 JSON、评分或权重。仅在当前源码支持且新任务采用 `stage-simulation-v1` 时，才按事先冻结的 `counterexample-acceptance-v1` 启用必达反例能力；该验证能力与 `decision_capability` 分开绑定。旧 legacy、B1、D1（`implementation-simulation-v1`）保持原合同，可给验收建议，不能静默启用新必达门禁或改模式。

宿主从已有 Requirement 义务或 spec/task 条目及其摘要取得判据，冻结合法输入域、前提、期望关系、业务观察方式和来源。按风险选择最多 3 项义务，每项最多 2 种错误机制；一批错误候选、一次有依据的 V1 验收强化。冻结所选与未覆盖集合、必达/建议属性、全部指定合法控制，以及输入、候选、资源初态和执行表；不能事后删去失败或未知项缩小分母。没有可靠判据的要求保留未知或原评审，不能靠自然语言猜测业务真值。

执行前保留原 V0 验收、当前真实成果及候选摘要，逐步列出 argv、cwd、输出、超时、阶段、尝试上限、资源权限和清理范围。全部尝试共享原预算，事前预留范围内业务修复、最终完整复验、原 R2 和清理；合法控制、无效/未知、失败、重试也计成本。资源隔离只覆盖声明的受控资源，不是可运行任意恶意代码的安全沙箱。

每个 exercise 须冻结 `binding.witness_input`：见证 ID、实际 argv 参数位置（从 0 计数且不得指向执行程序）和 `text` 或 `json` 编码。`text` 原样传递字符串，`json` 使用确定性的业务值序列化，十进制保持精确文本数值。运行前及证据消费时核对声明输入与完整参数；observe 必须依赖同一对象、同一阶段的已绑定 exercise，或为自身的只读命令提供输入绑定。写入持久资源的动作使用 exercise，随后由独立 observe 读回。所有业务读回归于该对象的同一见证；缺失或不同输入不得借合法见证标签通过。该绑定证明传入的参数，不证明被测程序确实消费该参数，实际行为仍须独立业务读回。

每个 acceptance 用 `business_observation_step_id` 明确绑定同对象、同断言、同阶段和同资源的 observe，并依赖该观察完成。观察与验收之间不得插入 reset 或新的业务执行。observe 与 acceptance 均保持受控资源只读，记录命令前后的完整资源内容摘要及尝试归属；验收前后须与所绑定观察的资源状态一致。V0 修改资源后 V1 对另一状态的拒绝不能算检出；缺少、变动或错配的原件不能算完成。文件与 SQLite 的持久状态均需核验，不能忽略数据库副文件。该证据说明步骤边界的一致性，不代替对观察、验收逻辑及其冻结来源的审查。

业务观察与验收断言分开：合法输入下的真实业务违约才构成有效反例，且对应目标断言确实拒绝才算检出。进程非零、编译失败、无关断言、协议坏包、绑定缺失或陈旧均不得冒充检出；保留 `UNKNOWN` 与原始材料。V1 必须识别目标有效反例、接受全部非空的指定合法控制且无未解决误拒；V0 原误拒可以修正，无新增有效证据则保留 V0，可选探索失败不冒充业务缺陷。

反例验收只将 `0..255` 的可移植退出码纳入正常完成资格，仍须完整原件与有效断言协议；其他原始退出码及材料保留供诊断读取，判 `UNKNOWN` 且不得支持检出或采纳，此限制不改变普通命令的退出码语义。

必需的 exercise、observe、reset 和 cleanup 均须成功退出；目标验收断言的明确拒绝按原判据单独解释。所有启用阶段的合法控制误拒保留原始引用，同来源的后续成功不能抹除；真实业务修复后须在原输入、初态与执行条件下完整重验，不能借更换摘要增加 V1 强化次数。

资源根必须是明确忽略的独立临时目录，不能包含受版本管理或受保护的文件，也不能覆盖项目元数据与证据。认领与删除前均核对实际目录和原归属，只忽略所有权标记不够。启动新资源使用前，累计所有历史尝试并预留当前必需分支和历史资源收尾的次数；清理也消耗原额度。每个已启动资源周期都须有匹配的终末清理证明，更换候选或只证明进程结束不能解除该义务。中断后由原验证入口处理原冻结清理：原进程已结束、原资源和执行来源未漂移、原时间与次数仍足够时，只执行尚未完成的清理，再推进当前计划；不重放旧业务或把未执行步骤记为成功。条件不满足时保留资源、原件及具体阻断。

当前成果确有业务违约时，在原授权范围修复，保留修复前 `FAIL` 及前后业务读回，再完成全部合法控制、最终复验和可交付防护；错误变体被检出不能覆盖真实成果失败。防护须引用实际验收文件/断言，运行中断、预算不足或必达未决时保留未完成。报告分别写意见、选择、已应用变更、实际观察和原 Close，交代真实问题、已修复/未修复项、所有合法控制、防护位置、未覆盖范围及追加时间、调用、返工与模型/人工成本；未知 token 或费用不填零。摘要与原始证据供原 review/Close 复核，不替代原门禁。

## 铁律

```
没有新鲜的验证证据，就不能声称完成。
```

如果你没有在当前步骤运行过验证命令，你不能说它通过了。

## 门函数

每次声称任何状态或表达满意之前：

```
1. 识别：什么命令能证明这个声称？
2. 运行：执行完整命令（新鲜的、完整的）
3. 阅读：完整输出，检查退出码，数失败数
4. 确认：输出是否支持声称？
   - 不支持 → 陈述实际状态 + 证据
   - 支持 → 陈述声称 + 证据
5. 然后才能：做出声称

跳过任何步骤 = 猜测，不是验证
```

## 验证矩阵

| 声称 | 需要的证据 | 不够的证据 |
|------|-----------|-----------|
| 测试通过 | 测试命令输出：0 failures | 上一次运行、"应该通过" |
| Lint 通过 | Lint 命令输出：0 errors | 部分检查、推断 |
| 构建成功 | 构建命令：exit 0 | Lint 通过、"日志看着正常" |
| Bug 已修 | 复现测试通过 | 代码改了、"应该修好了" |
| 既有能力未退化 | 既有入口 / 既有选项 / 既有输出的回归测试或真实命令证据 | 只验证新功能 happy path |
| 回归测试有效 | Red-Green 验证完成 | 测试通过一次 |
| 需求已满足 | 逐条检查清单 | "测试通过了" |
| 批次完成 | 所有任务标记 + V2 通过 + 审查通过 | 任务做完了 |
| 阶段完成 | 门禁 PASS + 产物齐全 | "应该差不多了" |

## 最小 fresh verification 画像

当变更范围不同，允许的最小 fresh verification 集合也不同；但**必须显式选择画像**，不得再靠“这只是 docs 改动”口头豁免。

- `docs-only`
  - 适用范围：仅改 `docs/**`、`specs/**.md`、`task-execution-log.md`、`tasks.md` 等 Markdown/收口文档。
  - 最小证据：`uv run ai-sdlc verify constraints`
  - 收口要求：若进入 close 阶段，`task-execution-log.md` 最新批次必须显式写 `验证画像：docs-only`，并在最终 `git commit` 后再运行 `workitem close-check`。
- `rules-only`
  - 适用范围：仅改 `src/ai_sdlc/rules/**.md` 与相关文档，不含 `src/**/*.py`、`tests/**`。
  - 最小证据：`uv run ai-sdlc verify constraints`
  - 收口要求：latest batch 必须显式写 `验证画像：rules-only`；若实际混入代码/测试改动，不得继续沿用本画像。
- `truth-only`
  - 适用范围：仅改 `.ai-sdlc/**`、`specs/**.md`、`docs/**.md` 等项目真值与 formal carrier，不含 `src/**/*.py`、`tests/**`。
  - 最小证据：`uv run ai-sdlc verify constraints`
  - 收口要求：latest batch 必须显式写 `验证画像：truth-only`；若混入代码/测试变更，不得继续沿用本画像。
- `code-change`
  - 适用范围：任何涉及 `src/**/*.py`、`tests/**`、生成逻辑或运行时行为的变更。
  - 开发批次最小证据：按下文「批次验证范围」选择 `uv run pytest <相关测试路径或用例>`，执行 `uv run ruff check`、`uv run ai-sdlc verify constraints`；记录选择依据和实际命令。
  - 最终交付证据：当前候选完整 `uv run pytest`、`uv run ruff check`、`uv run ai-sdlc verify constraints` 及项目/合同规定的其他最终检查；批次定向通过不能替代最终完整验证。
  - 退化防线：若变更触碰既有用户可见能力、CLI 输出、adapter 指引、配置字段、生成模板或文档主路径，必须补充既有入口 / 既有选项 / 既有输出的回归测试或真实命令证据；不得只验证新功能 happy path。
  - 收口要求：latest batch 必须显式写 `验证画像：code-change`；不得用 `docs-only` / `rules-only` / `truth-only` 伪装代码改动。

`close-check` 负责对 latest batch 的画像与 execution-log 中的 fresh evidence 做只读核验；普通用户项目使用默认的 `verify constraints`，AI-SDLC 仓库自身维护才显式使用 `verify constraints --profile self-development` 检查框架规则文档和 PR checklist 的一致性。

## Reconcile Smoke Contract

- `Existing Artifact Probe` 与 `ai-sdlc recover --reconcile` 属于仓库状态诊断输出契约；Windows offline smoke 依赖它们识别“安装成功，但当前仓库仍需 reconcile checkpoint”的已知停止场景。
- 变更上述诊断输出契约时，必须同步维护 `.github/workflows/windows-offline-smoke.yml`、`tests/integration/test_github_workflows.py` 与 `verify constraints` 的 reconcile smoke contract markers。
- CLI 若继续使用“已停止当前运行，避免基于过时 checkpoint 继续执行。”提示，也视为该契约的一部分；修改这条停止语义时，同样必须同步更新相关 smoke 判定。

## 阶段化验证要求

### 批次验证范围

开发批次的 V2 依据真实影响面确定，不因发生任意代码修改就自动执行全项目测试。修复先运行原失败用例，再验证受影响的既有入口、相邻消费者及必要兼容和 smoke 检查；新功能也须覆盖可能受影响的既有行为，不能只跑新增测试。执行前在现有日志记录选择依据、命令和未覆盖范围，失败与实际耗时一并保留。

项目自身规则或当前冻结合同明确要求的必跑项仍须执行。跨模块修改、影响面无法可靠界定、出现无法解释的回归时，应扩大检查到相关集成范围，必要时执行全量；不得凭成本偏好跳过已知影响。批次验证完成只支持该批次，不等于阶段、任务或 Close 完成。

本节统一规定批次清单中的验证范围；`batch-protocol.md` 的 Step 3、Step 4.5 等普通批次全量表述按本节执行。多 Agent 产物合并、阶段门禁及最终交付明确要求的完整检查保持不变，最终结果必须绑定当前候选。

### 批次级验证（EXECUTE 阶段内）

```
每个批次声称完成前：
  □ R1 验证完成（红灯 — 测试正确失败）
  □ V1 验证完成（绿灯 — 目标测试通过）
  □ V2 验证完成（按批次验证范围选定的回归与必跑项通过）
  □ 构建验证通过（如适用）
  □ 代码审查通过（见 rules/code-review.md）
  □ tasks.md 中对应任务已勾选
  □ execution-log 已记录
  □ git commit 成功
```

### 阶段级验证（每个 Stage 门禁前）

```
每个阶段声称完成前：
  □ 该阶段的所有产物已生成
  □ 产物内容非空且格式正确
  □ 门禁条件逐条检查（见 rules/quality-gate.md）
  □ 产物之间交叉引用一致（无悬空引用）
  □ checkpoint.yml 已更新
  □ 若本轮发现框架缺陷 / 代理违约 / 门禁暴露的流程缺口，已写入 `docs/framework-defect-backlog.zh-CN.md`
```

### 流水线级验证（Stage 6 CLOSE）

```
流水线声称完成前：
  □ 全量测试通过（最终运行，不是引用之前的结果）
  □ 构建成功（最终运行）
  □ tasks.md 中所有任务已勾选
  □ spec 中所有 FR 和 SC 已覆盖（逐条对照）
  □ execution-log 完整
  □ development-summary 已生成
  □ 最终 git commit 成功
  □ checkpoint.yml 已删除
```

## Smoke Test 协议

在以下时机执行 smoke test：

```
触发时机：
  1. 每个批次的 V2 中与实际影响面相关的 smoke 检查
  2. Stage 5 全部批次完成后的最终验证
  3. Stage 6 CLOSE 的最终确认

Smoke Test 内容（根据项目类型）：

Web 应用：
  □ 服务能启动（不报错退出）
  □ 健康检查端点返回 200
  □ 核心 API 能响应（至少一个端点）

CLI 工具：
  □ --help 能正常输出
  □ 基本命令能执行

库/SDK：
  □ 能被导入/引用（无编译错误）
  □ 核心函数能调用

如果项目类型不明确或无法运行：
  → 退化为「构建 + 全量测试」作为 Smoke Test
  → 不阻断，但在 execution-log 中记录"Smoke Test: 退化模式"

## 框架缺陷落盘协议

当你在当前变更中发现的不是“业务实现错误”，而是**框架缺陷、规则缺口、状态漂移、代理违约**时：

```
1. 先完成当前必要验证，不得凭印象声称“只是流程问题”
2. 判断是否命中以下任一触发：
   - 用户明确要求记录
   - 门禁 / verify / close-check 被框架问题阻断
   - 自检发现自己跳过了框架约束
3. 命中后，在 docs/framework-defect-backlog.zh-CN.md 追加结构化条目
4. 即使该问题已在当前轮次被及时拦截并修复，只要它曾真实出现并暴露框架缺口，也必须登记；不得因为“已经修好”而跳过 backlog
5. 条目中除现象/根因外，还必须写出 `未来杜绝方案摘要`，并在 `rule / policy`、`middleware`、`workflow`、`tool`、`eval` 中的一项或多项展开成可执行的防复发方案
6. 仅当本轮没有新增框架问题时，才允许不追加条目
```

不要把这类问题只留在对话里，也不要只写偏差登记而不进入主 backlog。
```

## 红旗 — 停下来做验证

以下任何用词/想法出现时，必须触发门函数：

- 使用"应该"、"大概"、"似乎"
- 在验证前表达满意（"好了！"、"完美！"、"搞定！"）
- 准备 commit/push 但没跑过验证
- 信任上一次运行的结果（"之前通过了"）
- 依赖部分验证推断全部通过
- 想着"就这一次不验证"
- 疲劳时想快点收工
- **任何暗示成功/完成的措辞，但你没有运行过验证**

## 自我合理化防御表

| 借口 | 现实 |
|------|------|
| "应该现在能工作了" | 运行验证 |
| "我很有信心" | 信心 ≠ 证据 |
| "就这一次" | 没有例外 |
| "Lint 过了" | Lint ≠ 编译 ≠ 测试 |
| "代理报告成功" | 独立验证 |
| "累了" | 疲劳 ≠ 借口 |
| "部分检查够了" | 部分证明不了全部 |
