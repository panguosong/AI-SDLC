# AI-SDLC 开发与发布合同

本约定只定义 AI-SDLC 仓库自身的普通开发与发布流程，不为普通用户项目增加治理负担。

## 开发边界

- 仓库源码是本地开发的控制实现，使用 `uv run ai-sdlc ...` 执行治理和验证。
- 每项变更使用独立分支或 worktree，保持变更范围可审查。
- 代码合入前运行相关测试、完整约束检查、lint 和构建验证。
- 不把本地凭据、运行缓存、临时证据或用户项目状态提交到仓库。

## 保留的复核能力

量化 Loop 沿用以下复核与关闭边界：

1. Local PR Review 在提交前调用独立本地代理检查当前 Git 变更。
2. 代码精简分析只给出建议，可因正确性和交付价值灵活突破，不阻断 Loop 或发布。
3. Requirement、Design Contract、Implementation、Frontend Evidence、Local PR Review 五类结果由 CLI 按内容选择最多两种专家角色，当前宿主 Agent 为每个角色自动启动独立只读上下文；专家只审查与 `input_digest` 同次读取返回的 `review_snapshot`，不得重新打开可变工件路径；同一结果最多一次修复后复审。

宿主 Agent 必须消费 `loop review` 返回的 `expert_roles`、`expert_reasons` 与 `round_number`，自动调用 `loop review-record`，不得要求维护者手动触发专家或搬运结果。宿主无法提供独立上下文、必要工具或有效判断时，必须报告阻塞，不得由作者自行给出 PASS。专家上下文和身份只存在于当前对话；框架仅在原 Loop 目录保存 `review-outcome-round-1.json` 和至多一个 `review-outcome-round-2.json`。系统不创建第三轮结果、review session、ledger、certificate、attestation、authority/store、Shadow/Enforce 激活状态或第二套 close 流程。

自 `v3.1.0` 起，新量化实例覆盖五个 Loop、六个评分视角：需求、设计合同、实施方案、代码成果、前端证据、交付就绪。宿主根据普通 `run` 的 Next 准备冻结输入、候选和独立判断，框架复算预测评分并检查有限成本准入；用户不手填 JSON、分数或预算。实际产物仍由原生门禁和实际 R1/R2 判断决定是否关闭，预测高分不能替代浏览器、测试或真实审查证据。旧实例不迁移、不重置合同和预算；已退役的历史 continuation 不恢复执行。

## Pull Request

- PR 必须说明目的、范围、测试结果和剩余风险。
- Local PR Review 的验证证据必须在动态专家复核之前记录，最终报告只在复核无可操作问题后生成。
- 专家不可用、超时或返回无效结果时，Loop 保持 `needs_review`；不得把失败解释为通过。
- 有发现时由原实现代理修复，并只允许一次复审；仍有问题则停止并报告，不进入无限对抗循环。
- 通过后由当前代理调用既有 close，再走普通 CI、分支保护和合并流程。

## v3.2.0 本次发行路径替代

维护者于 2026-09-15 明确授权，仅对本仓库本次发行取消当前本地整包 PR 完整复评、`pr-review` 原生提交和 Local PR 原 Close 三项发布前置，由真实 GitHub PR、当前提交上的 Codex review、完整 CI、合并及发行证据承接。上文与此冲突的本次执行顺序不再适用；普通用户产品的 Local PR 能力、正式复核、证据校验和 Close 保持原有要求。

- P1 自身仍须完成 Implementation 正式复核、正常 Close 和即时关闭回读，随后冻结原 HEAD、文件字节、模式和实际回执。原 P1 不执行普通 Git 提交，也不因发布修复重新打开。
- 只创建一个用于发布的隔离 checkout，逐路径核对允许公开的候选内容与文件模式，再使用普通 Git 提交。凭据、私有运行状态和临时历史材料不进入公开仓库。
- GitHub PR 必须如实说明变更、已知问题及回归证据、本地整包审查的技术失败和未完成事项。请求 `@codex review` 后确认实际响应与结果；接收表情或没有新增评论不能当作审查完成。线上审查聚焦 PR 差异与严重问题，不等同于全历史整包审查。
- 当前 PR 必须启动并通过完整 CI；Draft 的 Fast Gate 不替代完整兼容矩阵。线上发现的问题在发布 checkout 中作范围内修复，更新当前提交的测试、审查及 CI 证据。
- P1 原生关闭只证明冻结候选完成原流程；发布提交及其后续改动由线上审查、当前 CI 和安装版完整验收验证。GitHub SHA、评论和合并结果不得包装为原生 `VerifiedDeliveryCommit`。
- 本地 review 的 blocked、超时、历史发现、修复回执、原生计数和累计成本原样保留，不改成通过，也不伪造 findings、review outcome 或 `delivery_commit`。不再恢复已取消的本地整包调用及旧续办指令。

封版仍要求公开版本及三平台资产身份一致、干净安装后的真实量化选择与约束校验、真实反例及修复和回归拦截、同一最小需求的完整正常流程与 Close 回读全部完成。测试数量、预测分数和发布成功本身不能证明 ROI 或全局最优；服务连接或权限缺失须如实报告，不能降低门禁。

## 普通发布流程

新用户手册从 `v3.0.0` 之后的首个版本开始执行
[`新用户手册发布标准`](user-guide-release-standard.zh-CN.md)：必须覆盖全新空项目与已有项目、在线与离线安装、Windows/macOS/Linux 的 12 条自包含路线。任一路线缺失、不能从全新终端独立执行，或没有对应真实环境验证，均阻塞发布。

发布使用 `.github/workflows/release-build.yml` 和 `.github/workflows/release-artifact-smoke.yml`：

1. 从已通过保护检查的 main 提交创建精确版本 tag。
2. 为该 tag 创建新的空 Draft Release，不复用历史 Draft。
3. 构建 wheel、sdist 和三个目标平台的离线包。
4. 在 Windows、macOS、Linux 执行安装与 smoke。
5. 仅把通过 smoke 的三个离线包及其三个 checksum 上传到 Draft Release。
6. 下载 Draft 的六个资产并核对名称、sidecar 与 SHA256；制品或构建 smoke 失败保持 Draft，不改写 tag。只读 token 无法读取 Draft 时，不能把可见性失败记为通过，也不增加权限或盲目重试；保留构建 smoke 与资产校验证据。
7. 由明确授权的维护者重新核对 main、精确 tag、Draft 和六资产身份后发布为 latest，等待发布事件触发的三平台制品 smoke；再分别手动触发 `windows-user-guide-e2e.yml` 与 `posix-user-guide-e2e.yml`，输入 `tag=v3.2.0`。两份用户指南 E2E 不会由 release 事件自动触发，全部通过后才宣布发布完成。

发布流程不生成 Release Proof、Permanent Certificate、generation burn、release attestation 或额外 authority 指针。GitHub Release、tag、普通 CI 和分支保护是发布所需的现有平台能力。

## 当前基线与发布身份

本公开源树以已发布 `v3.1.0` 为代码基线，当前发行目标为 `v3.2.0`。重新导入源树不创建或补发历史 Release，也不继承历史提交的 Close 身份。正式稳定版本以精确 tag、GitHub Release 和该提交的实际验收结果为准。



发布变更必须同步检查 `README.md`、`USER_GUIDE.zh-CN.md`、`packaging/offline/README.md` 和 `docs/pull-request-checklist.zh.md`。项目地址固定为 `https://github.com/panguosong/AI-SDLC`。

- `ai-sdlc-offline-3.2.0-windows-amd64.zip`
- `ai-sdlc-offline-3.2.0-macos-arm64.tar.gz`
